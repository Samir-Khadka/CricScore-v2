## 2. Findings, ordered by severity

### F-1 · HIGH — Ownership + mass-assignment gaps on all non-scoring CRUD
Authentication is enforced (routes sit behind `checkAuthCookie`,
`server/index.js:66-70`), and the *scoring* path enforces ownership
(`services/scoringService.js:158` `assertOwnership`, used at :282 and :371).
Nothing else does:

- `controllers/matchController.js:79-83` — `handleUpdateMatch` runs
  `findByIdAndUpdate(matchId, { $set: req.body })`: any logged-in scorer can
  rewrite **any** match, including `winner`, `result`, `matchState`,
  `createdBy`.
- `controllers/matchController.js:96-107` — `handleDeleteMatch` deletes any
  match by id, no ownership check (and no cascade — innings/ball events are
  orphaned).
- `controllers/matchController.js:39-57` — `handleGetMatches` lists matches
  for an arbitrary `:scorerId` URL param.
- `controllers/matchController.js:182-202` — `handleUpdateMatchState` flips
  any match's state, no ownership check.
- `controllers/tournamentController.js:28-34` — update takes the target id
  *from the request body* (`tournamentUpdate._id`) with `{ $set: req.body }`;
  :61 deletes any tournament; :158 deletes any team; :172-173 updates any
  team with `$set: req.body`.
- `controllers/playersController.js:74` — deletes a squad document by id,
  no ownership check.

This is a partial survival of the old review's C-2 (IDOR + mass assignment):
fixed on the ball-by-ball path, untouched on the CRUD surface.

### F-2 · HIGH (workflow) — `npm test` is broken and nothing runs it
`server/package.json` declares `"test": "node --test tests/"`. On Node
v24.22.1 (this machine) that fails instantly:
`Error: Cannot find module '…/server/tests'` — 0 tests run. The suite itself
is healthy: `node --test tests/scoringEngine.test.js` (or a glob) gives
**24/24 pass**. There is no CI (no `.github/` in the tree; deploys are
platform auto-deploys), so the broken command is the only test gate and it
gates nothing. README still documents the broken command and says "20
cases" — the count is 24.

### F-3 · MEDIUM — Points table N+1 (inconsistent with the same file)
`controllers/viewerController.js:202` runs `await Innings.find({ matchId })`
**inside** the per-match loop of `handleGetPointsTable` — one query per
completed match. The leaderboard handler in the same file batches correctly
with `{ $in: [...] }` (`viewerController.js:263`). The table is also fully
recomputed on every request (acceptable at local-tournament scale; the N+1
is the concrete defect).

### F-4 · MEDIUM — God files
- `user/src/pages/ManageTournament.jsx` — 1,045 lines
- `user/src/pages/ScorerConsole.jsx` — 1,004 lines
- `user/src/pages/Match.jsx` — 792 lines
- `server/engine/scoringEngine.js` — 578 lines, of which
  `computeInningsState` alone is ~330 lines (a single pure fold — cohesive,
  but the natural next split is validation / per-ball application / derived
  aggregates).
- `server/controllers/viewerController.js` — 354 lines mixing public reads,
  points-table maths, leaderboards and milestones.

### F-5 · MEDIUM — No route-level code splitting
`user/src/App.jsx` statically imports all 13 pages; `React.lazy`/`Suspense`
count in `user/src` is **0**. Verified build output: one JS chunk,
**464.8 kB (132.1 kB gzip)** + 63.3 kB CSS — every casual viewer downloads
the scorer console, organizer pages and chart code. (Old review F-31, still
true.)

### F-6 · MEDIUM — Live-update path does redundant work at both ends
Per ball, `controllers/ballByBallController.js:6-18` (`emitLive`) runs two
fresh DB queries — all innings for the match **and all live matches** — and
emits them. The client then ignores the payload: `pages/Match.jsx:184-195`
refetches the full match detail on every `matchLiveUpdate`. Correct, but
chatty, and the home-room fan-out cost grows with every concurrent match.

### F-7 · MEDIUM — Match creation falsely rejects unrelated matches
`controllers/matchController.js:9` checks duplicates with
`Match.findOne({ match_time, match_date })` — global across all tournaments
and scorers. Two different tournaments cannot schedule a match at the same
date + time; the second create gets a 422 "Match already exist".

### F-8 · MEDIUM — Coverage gaps around the riskiest untested code
The engine is the only tested unit (see §4). Untested:
- `services/scoringService.js` `normalizeEvent` (lines 41-118) — the
  legacy-payload translation layer ("nb+2b" byes folding, run-out variants).
  This is intricate, spec-critical code with zero tests.
- All controllers / API integration (auth status codes, ownership 403,
  idempotent replay, optimistic-concurrency 409).
- Points-table / NRR maths in `viewerController.js`.
- The entire frontend (no test script in `user/package.json`).

### F-9 · LOW — HTTP status semantics
`422` is used 30× server-wide vs `401` once. Unauthenticated requests get
422 (`middlewares/authenticate.js:8-10`), so clients cannot distinguish
"log in again" from "invalid input". `authenticate.js:15` also embeds the
raw JWT error (`"Error: " + error`) in the response body.

### F-10 · LOW — Debug logging residue
29 `console.*` calls in server code (excl. node_modules/tests), mostly
`console.log(error)` in catch blocks. Worst: `controllers/matchController.js:112`
`console.log(req.body)` and :117 (inside `handlePreMatch`, which is itself
dead — its route is commented out at `routes/matchRoute.js:26-27`). The
frontend is clean: **0** `console.log` in `user/src`.

### F-11 · LOW — Dead / legacy residue
- `server/services/CreateInning.js` is imported by `routes/matchRoute.js:14`
  (`startInning`) but wired to no route; its header comment names the wrong
  file ("// controllers/inningsController.js").
- `client/` (legacy CRA) still sits in the workspace tree; README's
  Installation section still leads with it before the modernization note
  explains it is reference-only.
- Deployment artifacts (root `index.html`/`assets/`) exist only in the
  GitHub repo / `user/dist`, not at the workspace root.

### F-12 · LOW — Naming and envelope drift
- `server/models/Tournment.js` — the pre-existing typo survives.
- `UserRouter.js` / `UserController.js` are PascalCase; all siblings are
  camelCase.
- `matchController.js:71` returns `{ Match: match }` while the rest of the
  API uses `{ message, data }`.
- `handleUpdateMatchState` (`matchController.js:186`) accepts `"scheduled"`
  and `"pause"` states the rest of the stack never uses (canonical set is
  `upcoming | live | completed` — the casing lesson documented at
  `matchController.js:157-161`).

### F-13 · LOW — Index keys in lists
`key={i}` appears in ~10 places (`PointsTable.jsx:24`, `MatchDetails.jsx:41`,
`Scorecard.jsx:124`, `Partnerships.jsx:31`, `ManageTournament.jsx:290`, and
`TimelineItem` lists in four files). Impact today is small — the lists are
append-only or stateless (points-table rows hold no local state) — but the
sorted points table is exactly the pattern that bites when a row gains
state. Stable ids exist (`o.over` is used correctly in `Match.jsx`'s
Manhattan chart).

### F-14 · LOW — Focus visibility and landmarks (a11y)
Only **1** `focus:` utility in 9,090 lines of JSX. Native `<button>`s keep
the UA focus ring, but custom tab/pill controls (e.g. Match page TABS,
`pages/Match.jsx:47-52`) lean on hover styles. Landmarks: `<nav>`
(`NavBar.jsx:54`) and `<footer>` (`Footer.jsx:9`) exist; page content is
not wrapped in a `<main>` landmark.

### F-15 · INFO — Narrow sequence race in ball posting
`scoringService.postBall` assigns `sequence = countDocuments + 1`
(`scoringService.js:291,313`). The `(inning, sequence)` index
(`models/BallEvents.js:70`) is not unique, so two truly simultaneous posts
that both omit `expectedSequence` could collide. In practice the UI always
sends `expectedSequence` (409 guard) and `clientEventId` retries are
deduped by a partial unique index (`BallEvents.js:71-74`) — a theoretical
gap, not an observed defect.

### F-16 · INFO — Live/workspace parity
- Frontend: `https://cricscore-v2.wasmer.app` → HTTP 200.
- API: `/api/cricscore/view/tournaments` and `/view/matches` return the
  Urlabari Premier League 2026 data seeded by `tools/seed-production.js` —
  the live API matches this workspace's generation of the code.
- There is no `/health` endpoint (returns the JSON 404); Render's
  health-check path is `/api/cricscore/view/tournaments` per `render.yaml`.
- Socket.io rooms are unauthenticated by design (public live data);
  emission pattern is F-6.

## 5. React lens — detail

Done well (vercel-react-best-practices priorities):
- **No waterfalls where it matters:** `Home.jsx:112-119` fires its four
  section fetches in parallel; `ScorerConsole.jsx:108,119` and
  `MatchSetup.jsx:155` use `Promise.all` for squads and innings. The one
  sequential chain (`ScorerConsole.loadAll`: match → squads/innings) is a
  true dependency.
- **Abort discipline:** `api.js` threads `AbortSignal` through every call;
  pages create an `AbortController` per effect (e.g. `Match.jsx:176-182`).
- **Socket hygiene:** `Match.jsx:184-195` keys the socket effect on
  `matchId`, tracks connection state, and disconnects on cleanup (old
  F-04 fixed). `Home.jsx:128-141` same pattern.
- **Derived state via `useMemo`, not effects:** innings views, team views,
  active innings (`Match.jsx:197-230`) — the old F-29 pattern is gone.
- **Central API layer** (`lib/api.js`): `ApiError` with status/body,
  envelope `unwrap`, credentials included — old F-30 fixed.
- Memoization is used broadly but not cargo-culted (51 `useMemo`/
  `useCallback` across 10 files, concentrated in the heavy pages).

Gaps: F-5 (no splitting), F-6 (refetch-on-event instead of applying the
socket payload), F-13 (index keys).

## 7. Prioritized fix list

1. **Close the CRUD authorization gap (F-1).** Reuse the
   `assertOwnership` pattern from `scoringService` on every match /
   tournament / team / players update, delete and state endpoint; replace
   `$set: req.body` with per-resource field allowlists; take target ids
   from the URL, never the body.
2. **Fix the test entry point and add CI (F-2).** Change the script to
   `node --test tests/scoringEngine.test.js` (or a glob), and add a
   GitHub Actions workflow running server tests + `user` lint/build on
   every push — deploys currently ship with no automated gate.
3. **Test the translation layer and the API contract (F-8).** Unit tests
   for `normalizeEvent` (legacy shapes incl. "nb+2b", both run-out
   variants), plus a thin API suite: 401 without cookie, 403 for
   non-owner scoring, idempotent replay returns `duplicate: true`,
   `expectedSequence` mismatch returns 409.
4. **Batch the points-table query and trim live-update chatter (F-3,
   F-6).** Copy the `$in` batching already used at
   `viewerController.js:263`; have the client apply the emitted innings
   payload (or debounce refetches to one per second).
5. **Split the bundle by route (F-5).** `React.lazy` for
   `ScorerConsole`, `ManageTournament`, `MatchSetup` and `Match` — the
   viewer-first chunk should drop well under half its current 465 kB.

Quick wins after those: fix the global duplicate check (F-7) by scoping
it to tournament + teams; standardize 401 for auth failures (F-9); delete
`handlePreMatch`'s debug logs and the dead `CreateInning` import (F-10,
F-11); correct the README badges and test count (§3).

## 8. What is genuinely strong

- **The scoring engine is the real thing.** A pure, deterministic fold
  over the event log with law validation *inside* the fold (dismissal
  legality per delivery type, bowler quotas, crease bookkeeping,
  retired-hurt returns) — and tests that read like a casebook of every
  bug the old system ever had.
- **Event sourcing done pragmatically.** Snapshot rebuild after each
  ball, undo-by-void with an audit trail, and a rollback if the engine
  rejects a ball (`scoringService.js:332-338`). The scorecard *cannot*
  drift from the log by construction.
- **Idempotency + optimistic concurrency, end to end.** The console
  mints one `clientEventId` per tap with retry reuse
  (`ScorerConsole.jsx:57,303-317`); the server dedupes it under a
  partial unique index and rejects stale scorers with 409. This is the
  correct answer to double-taps on flaky tournament Wi-Fi.
- **Configuration discipline.** `config.js` fails fast in production on
  a missing/default JWT secret; rate limits, helmet, body-size caps
  and a stack-free central error handler are all in `index.js`.
- **The frontend grew up.** Central API layer with aborts and typed
  errors, parallel data loading, socket cleanup, memoized view models,
  loading/error states everywhere, mobile navigation, a working
  class-driven dark mode, and accessibility that went from "zero
  semantics" (old review) to labels/aria/landmarks in one rebuild.
- **Backwards compatibility without rot.** Legacy CRA payloads are
  translated at one boundary (`normalizeEvent`) instead of leaking
  snake_case through the system.
