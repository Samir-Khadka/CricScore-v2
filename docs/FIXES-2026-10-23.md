# CricScore — Fixes, 2026-10-23

Fix batch for every finding in `ANALYSIS-2026-10-23.md` (Samir: "solve
all the error"). All changes verified locally; shipped to
`Samir-Khadka/CricScore-v2` main and redeployed (Render API + Wasmer
static bundle rebuilt from the new build).

## F-1 · HIGH — Ownership + mass-assignment on non-scoring CRUD — FIXED

New shared helper `server/services/ownership.js` (`pickFields`,
`isOwner`, `loadOwned`) applies the scoring path's ownership rule to
the whole CRUD surface:

- `matchController`: update/delete/state/selectXI load the match,
  return **404** when missing and **403** when `createdBy` ≠ caller;
  updates pass an allowlist (`match_date, match_time, venue, teamA/B,
  teamA_id/B_id, toss, umpires, matchRefree`) — `winner`, `result`,
  `matchState`, `createdBy`, `innings`, `playingXI` are no longer
  writable through the generic update. Delete cascades to the match's
  innings + ball events (no more orphans). `handleGetMatches` refuses
  to list another scorer's fixtures (403 when `:scorerId` ≠ token id).
- `tournamentController`: update/delete take the id from the **URL**
  (`PUT/DELETE /tournament/:id`), allowlist applied, ownership
  enforced; tournament delete cascades (teams, squads, matches,
  innings, ball events). Team update/delete moved to
  `PUT/DELETE /tournament/teams/:teamId` with the same rules; team
  create now checks the parent tournament exists (404) and is owned
  by the caller (403). Team delete also removes its squad sheet.
- `playersController`: squad add/update/delete resolve the parent
  tournament and enforce its ownership. Update ids come from the URL
  (`PUT /players/:tourId/:teamId`; `user/src/lib/organizer.js` updated
  to match). Delete returns 404 when the squad doesn't exist.
  Duplicate-squad create now returns 409 (was 500).
- `matchController.handleCreateMatch`: creating a match in someone
  else's tournament is 403; missing tournament 404.
- Audit extras: `scorerController.updateScorer` was an unauthenticated
  "edit any profile by email" endpoint — it now sits behind the
  session cookie and only ever updates the caller's own record;
  profile-image upload likewise requires auth + matching email.
- Verified by the API suite (below): 403 for every non-owner write,
  allowlist drop of `winner`/`matchState`/`createdBy` proven in a
  response-body assertion, 404s for missing resources.

## F-6 · MEDIUM — Live-update waste — FIXED (client coalescing)

The socket payload is the raw innings snapshots; the Match page
renders engine-derived state/events/milestones that only the detail
endpoint computes, so applying the payload directly would mean
duplicating the engine fold in the browser. Chosen fix (the simpler
correct option): `Match.jsx` now **coalesces** refetches — a burst of
ball events collapses into one silent refetch (350 ms trailing
window), and a refetch already in flight is followed by at most one
more. Viewer behaviour is identical; request volume per ball drops
from N events → ≤1 fetch. The home page already applies its
`liveMatches` payload directly and was left as is. Server-side
`emitLive` still re-queries per ball for the two rooms — acceptable
at tournament scale and now harmless to viewers.

## F-7 · MEDIUM — Global duplicate-match rejection — FIXED

`handleCreateMatch` scopes the `{ match_date, match_time }` check to
the match's own tournament (`+ tournament_id`). Two different
tournaments can now schedule at the same date/time; a duplicate
inside one tournament still returns 422. Both directions are covered
by API tests.

## F-15 · INFO — Sequence race — NOTED, no change

As the analysis concluded: theoretical only. The UI always sends
`expectedSequence` (409 guard, now API-tested) and `clientEventId`
retries are deduped by the partial unique index. Making
`(inning, sequence)` unique would break the undo-by-void flow
(voided balls keep their sequence numbers), so the current design
stands.
