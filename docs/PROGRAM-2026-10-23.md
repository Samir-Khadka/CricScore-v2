## Phase 1 — Architecture (improve-codebase-architecture + code-review)

Behaviour-preserving extractions only; the existing 59/59 server suite
and lint were the safety net (no frontend tests existed yet — Phase 4).

**Frontend**
- `lib/cricket.js` gained the match-detail composition as one deep
  module: `detailViewModel(detail)` → `{ entries, views, viewFor,
  activeIndex, activeEntry, activeView }`, `activeInningsIndex(entries)`,
  and `teamAWinPct(match, entries)`. Previously `Match.jsx` and
  `FeaturedMatch.jsx` each hand-composed per-innings views and the
  hero re-derived win probability with its own (divergent) rules. Both
  now consume the shared module.
- `lib/organizer.js` gained `fetchScorerMatches(scorerId, { signal })`
  (owns the `GET /match/:id` fan-out; a 404 match contributes nothing)
  and `filterTournamentMatches(list, tournamentId, tournamentName)`
  (id match, name fallback). ManageTournament carried two duplicated
  inline copies of the filter; ScorerMatches hand-rolled the fetch.
- New `hooks/useMatchLiveUpdates.js` — owns the match socket listener,
  the 350 ms trailing coalesce, the in-flight guard, and the
  connected flag. Match.jsx's socket/timer/ref plumbing is gone; the
  page supplies only its fetcher.
- New `lib/scorer.js` — the scorer console's pure selection rules
  (`outBatsmanIds`, `pickCreaseSelection`, `batsmanDisabledIds`,
  `bowlerDisabledIds`) extracted from ScorerConsole's sync effect and
  picker props, where they were entangled with page state.

**Server**
- New `services/httpError.js` — `httpError(status, message)` +
  `sendHttpError(res, error)`. scoringService imports the shared
  `httpError` (its local copy deleted); ballByBallController's three
  identical catch blocks collapsed onto `sendHttpError`.

**Deliberately left** (documented in ARCHITECTURE): CRUD/viewer
controllers keep per-endpoint error messages — they are the public API
surface, and flattening them would change client-visible text; Home's
multi-resource loader stays inline (a generic hook would be shallower
than the code it replaces); the ScorerConsole state machine stays
in-page; legacy `client/` untouched.

## Phase 2 — Design completion (web-design-guidelines + Floodlit)

Surfaces audited: the earlier passes had already put viewer *and*
organizer surfaces on the shared token layer, so the honest scope of
this phase was the remaining drift plus the surfaces that genuinely
lacked the system. There is no profile page/route in the app — nothing
existed to treat there.

- **Token sweep:** 41 rendering-identical swaps across 11 files —
  raw `#10b981` → `emerald-500`, `#a3e635` → `lime-400` in class
  strings. Raw hex now survives only in SVG gradients and the
  `TEAM_COLOR_HEX` data table, where hex is the correct format.
- **NotFound rebuilt** on the design system: surface-card panel,
  gradient icon chip matching the app's VS-medallion idiom,
  condensed display-type 404, `.btn-primary` home link plus a
  secondary "Live matches" link (existing route).
- **ErrorBoundary:** off-system hex CTA → `.btn-primary`; icon in a
  rose chip; title moved to the display face.
- **Login:** "Scorer Account" eyebrow + condensed uppercase title,
  matching organizer typography.
- **ScorerConsole:** innings-tab active tone emerald-600 → emerald-700
  (the design system's AA active-tab tone).
- **Shared CTA unification** (from the Phase 4 review): the gradient
  CTA is now adopted from `formStyles.primaryBtnCls` /
  `primaryBtnInlineCls` in ScorerMatches (5 sites) and
  ManageTournament (2 sites) instead of being re-declared inline.
  Deliberate variants remain: PickerSheet's taller sheet CTA
  (min-h-14) and gradient *toggle chips* (squad sheet, XI picker) —
  different component roles, same tokens.
- **AA fix:** the Login and ManageTournament eyebrows moved from
  emerald-500 (fails AA at 12 px) to emerald-600 / dark:emerald-400.
- Audit conclusion: scorer sheets/modals already share one shell
  (backdrop blur, slide-up, card panel); organizer bits form a coherent
  sub-system; both themes ride the same CSS-variable tokens.

## Phase 3 — Performance (vercel-react-best-practices)

Measured first: baseline entry 342,938 B (gzip ~105 kB), CSS 78.53 kB.

- **Match-detail prefetch on intent:** `lib/api.js` gained a one-shot
  prefetch cache (`prefetchGet`, 15 s TTL, failures fall back to a real
  fetch, promise never rejects); `lib/preload.js` exposes
  `prefetchMatch(id)` + `matchPrefetchProps(id)` (mouse-enter / focus /
  touch-start), spread onto the match-card links in ScoreSummaryCard,
  Recent, Upcoming, FeaturedMatch. Hovering or touching a card now warms
  both the Match route chunk and its detail payload.
- **Socket re-render scope:** `memo()` on the eleven match/home subtree
  components whose props are primitives or identity-stable across
  socket ticks (Features, HowItWorks, TournamentSpotlight, Commentary,
  TeamChip, TimelineItem, PlayerScoreCard, WinMeter, WormChart,
  Partnerships, Scorecard) — a live tick on Home or a detail refetch on
  Match no longer re-renders the static and chart subtrees.
- **content-visibility:** `.cv-auto` utility applied to Home's long
  marketing sections and Match commentary over-groups (the
  `rendering-content-visibility` rule from the skill's own guide).
- **Audits with no-change conclusions:** fonts (single css2 request,
  preconnect + `display=swap` already correct; Google's URL rotation
  makes hand-preloads brittle); icons (lucide named imports already
  tree-shake per icon); route lazy boundaries (already per-page from
  the earlier fix pass).

**Result:** production entry **344.18 kB** (gzip 105.31 kB), CSS
**78.24 kB** — +1.2 kB (+0.35%) over the 343.0 kB pre-program build,
buying the prefetch + memo infrastructure. Route chunks: Match
~31.1 kB, ScorerConsole ~27.8 kB, ManageTournament ~22.1 kB.

## Phase 4 — Tests + review (tdd + code-review)

- **Vitest added** (vitest + jsdom + Testing Library), `npm test` in
  `user/`, wired into CI — the user job is now *lint + test + build*.
- **54 frontend tests, all passing:** `lib/cricket` (inningsView both
  state shapes, ball labels/symbols, event summaries, team colours,
  detailViewModel, teamAWinPct), `lib/organizer` (roles, name parsing,
  duplicate detection, matchHasXI, filterTournamentMatches),
  `lib/scorer` (selection rules), and render tests for the three match
  card states (live / completed / upcoming) built from real
  list-payload shapes.
- **Server suite stays 59/59** (24 engine + 11 normalizeEvent + 24 API;
  run file-by-file on this VM for RAM reasons — CI runs the combined
  suite).
- **Two-axis code review** over the full program diff (~63 files):
  - *Fixed:* prefetch cache originally discarded the caller's
    AbortSignal (now honours it); CTA duplication (above); eyebrow AA;
    NotFound off-idiom values; a speculative unused parameter on
    `sendHttpError`; duplicated active-index derivation (now
    `activeInningsIndex`); the cryptic `vm` name → `detailModel`; a
    single-use middle-man wrapper inlined.
  - *Rejected with reasons:* "blanket memo is speculative" — in this
    tree the memoised components are children of socket-driven parents
    (Home re-renders on every live event; Match on every refetch), so
    each memo has a named trigger. "Prefetch cache makes api.js
    divergent" — the cache must live with `api.get` (its consumer);
    moving it creates a circular import. "`teamAWinPct` winner rule
    changes behaviour" — verified against the server: `winner` is
    assigned only in the same block that sets
    `matchState = "completed"`, and undo clears winner + result
    together, so no live payload can carry a winner. "Prefetch /
    content-visibility / 404 link change behaviour, violating the
    design docs" — those no-behaviour rules governed the earlier
    visual passes; this program's brief explicitly specifies
    intent-prefetch and the Vercel rules.

**Known issues surfaced, deliberately NOT fixed (behaviour changes,
Samir's call):**
1. `ScorerConsole` reads `view?.awaitingBatsman`, but `inningsView`
   never surfaces the engine's `awaitingBatsman` — so the
   retired-batsman exclusion in the picker never fires. One-line fix
   in `inningsView` when approved.
2. The server has no `/health` endpoint; Render health-checks a
   viewer route.

## Competitor gap table — honest assessment

Cricbuzz, ESPNcricinfo and Fancode are media platforms with
editorial teams, data feeds and native apps. CricScore is a scoring
*tool* for local leagues. Claiming parity would be false; the table
says where it actually stands.

| Capability | Cricbuzz / Cricinfo / Fancode | CricScore-v2 today |
|---|---|---|
| Create & score your own tournament | No — closed editorial data only | **Yes — ahead.** Anyone can register, create a tournament, add squads, and score ball-by-ball |
| Ball-by-ball scoring engine with cricket-law validation | Professional data feeds | Yes — event-sourced engine, extras/dismissal law checks, undo, two-scorer conflict guard |
| Live match page (scorecard, commentary, worm, partnerships, win probability) | Yes, richer | Yes — all present, real-time via sockets |
| Points table & player leaderboards | Yes | Yes — derived from completed matches |
| Local-league relevance (Nepali club cricket) | None | **Yes — ahead by design** |
| Editorial content: news, articles, video, interviews | Extensive teams | **None — real gap** |
| International/domestic pro coverage & historical archives | Decades of data | **None — real gap** (only self-created tournaments) |
| Native mobile apps + push notifications | Yes | **No — real gap** (responsive web + mobile nav only; no push) |
| Player profiles / career stats across tournaments | Deep | Partial — leaderboards per tournament; no cross-tournament career pages |
| Scale, CDN, uptime | Global infrastructure | Render/Wasmer free tiers; API sleeps when idle — **real gap** for concurrent live traffic |
| Monetisation / ads / subscriptions | Yes | None (not a goal today) |

**Verdict:** for its actual job — a local league or college tournament
that wants professional live coverage it controls itself — CricScore
is now a complete, coherent product: one design language across viewer
and scorer surfaces, a tested engine, a tested frontend core, and a
measured performance profile. Against the named competitors as
*media platforms* it is not #1 and this program did not make it so:
the gaps above (content, coverage, native apps/push, infrastructure
scale) are product-scope gaps, not code-quality gaps. Within its
category — self-serve local-league scoring — the combination of a
law-validating engine, full organizer flow, and broadcast-style live
pages is genuinely competitive.
